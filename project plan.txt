Below is a comprehensive project plan for building a UK Taxonomy Rule Discovery and Validation Workbench.
The framing is deliberately not “build a validator that rejects filings”. The stronger framing is:
Build a taxonomy-aware rule discovery, consistency checking, and modelling-improvement system for UK digital accounts.
That keeps it aligned with the FRC consistency-check philosophy: the historical consistency checks were intended to identify possible gaps, errors or weaknesses in tagging, not to act as hard acceptance/rejection validation tests.

Project Plan: UK Taxonomy Rule Discovery and Validation Workbench
1. Project purpose
The project will create a system that can:
1. Load the UK 2026 taxonomy suite from the local repo.
2. Discover topics from taxonomy hypercubes.
3. Extract the dimensional model for each topic.
4. Generate candidate rules from those models.
5. Run selected rules against iXBRL/XBRL filings.
6. Report findings as warnings, suggestions, or modelling-improvement opportunities.
The system should help answer questions like:
Has the filer used the taxonomy model that exists for this disclosure?

Are the concepts and dimensions used in the filing consistent with the relevant hypercube?

Has the filer used a flat tagging approach where the taxonomy provides a dimensional note model?

Are there missing total members, missing note anchors, or under-modelled disclosures?

Where could the filer improve the tagging by using existing UK taxonomy concepts, dimensions or members?

2. Core design decision
The project should be hypercube-first.
Earlier we considered generating rules from presentation and calculation relationships. We have now refined that.
For UK taxonomies:
Hypercube names identify topics.
Hypercube primary items identify the disclosure scope.
Hypercube dimensions identify expected note construction.
Domain-member trees identify possible member roll-ups.
Presentation ELRs provide context and human explanation.
There are no calculation linkbase relationships to rely on.
So the architecture should not be calculation-linkbase-led.
The design principle is:
Hypercube-first, presentation-explained, review-controlled.

3. Important terminology
3.1 Candidate rule
A rule generated automatically from the taxonomy structure.
Example:
The PPE hypercube has a PPE classes dimension.
If PPE note facts are present but no PPE class dimension is used, this may be weak modelling.
Candidate rules require review before being treated as production-quality checks.
3.2 Reviewed rule
A candidate rule that has been reviewed, accepted, edited or promoted.
3.3 Suppressed rule / anti-rule
A rule that prevents bad automated inference.
Example:
Do not treat missing dimensional combinations as nil.
Do not assume presentation children sum to a parent.
Do not infer a roll-up where another dimension is aggregated.
3.4 Finding
A result emitted when a rule runs against a filing.
Example:
Finding: PPE facts are present, but the expected PPE class dimension was not used.
Severity: info
Confidence: medium
Suggested action: consider using the PPE classes dimension.

In scope

3.2 Candidate rule families
Family 1 — Topic / note presence candidates
Purpose:
If a PFS concept is present, and the taxonomy provides a related note model, check whether note-model concepts are also present.
Example:
id: AUTO.PPE.NOTE_EXPECTED.001
type: note_presence_candidate
topic: property_plant_and_equipment
trigger:
  any_present:
    - core:PropertyPlantEquipment
expect:
  any_present_from_hypercube: core:PropertyPlantEquipmentHypercube
severity: info
confidence: medium
requires_review: true
Family 2 — Hypercube conformity
Purpose:
Check whether dimensions and members used in the filing are consistent with the cube model.
Example:
id: AUTO.PPE.CUBE_CONFORMITY.001
type: hypercube_conformity
topic: property_plant_and_equipment
hypercube: core:PropertyPlantEquipmentHypercube
check:
  dimensions_must_be_from_cube: true
  members_must_be_in_domain_tree: true
severity: warning
confidence: high
requires_review: false
Family 3 — Expected dimension usage
Purpose:
If several primary items from a note hypercube are present, expect at least one cube dimension to be used.
Example:
id: AUTO.PPE.DIM_EXPECTED.001
type: expected_dimension_usage
trigger:
  primary_items_from_hypercube_present:
    minimum_count: 2
expect:
  at_least_one_dimension_from_hypercube_used: true
severity: info
confidence: medium
Family 4 — Member validity
Purpose:
If a dimension is used, check the member belongs to the taxonomy domain tree.
Example:
id: AUTO.PPE.MEMBER_VALIDITY.001
type: dimension_member_validity
dimension: core:PropertyPlantEquipmentClassesDimension
allowed_members:
  from_domain_member_tree: true
severity: warning
confidence: high
Family 5 — Total member presence
Purpose:
If several component members are used, suggest the relevant total member.
Example:
id: AUTO.PPE.TOTAL_MEMBER_EXPECTED.001
type: total_member_presence_candidate
dimension: core:PropertyPlantEquipmentClassesDimension
trigger:
  component_members_present:
    minimum_count: 2
expect:
  head_member_present: core:TotalPropertyPlantEquipment
severity: info
confidence: medium
Family 6 — Dimension-member roll-up candidates
Purpose:
For one primary concept, one period, one unit and one dimension, check whether a total member appears to equal component members, holding all other dimensions constant.
Example:
id: AUTO.PPE.DIM_ROLLUP.001
type: dimension_member_rollup_candidate
dimension: core:PropertyPlantEquipmentClassesDimension
head_member: core:TotalPropertyPlantEquipment
component_members:
  from_domain_member_children: true
match:
  primary_item: same
  period: same
  unit: same
  all_other_dimensions: same
missing_policy: do_not_treat_missing_as_zero
safe_only: true
severity: warning
confidence: medium
requires_review: true
This is a consistency check, not a formal calculation-linkbase validation.
Family 7 — Dimensional aggregation safety
Purpose:
Prevent unsafe roll-ups where multiple dimensions are present.
Example:
id: AUTO.PPE.SAFETY.001
type: dimensional_aggregation_safety
when_summing_dimension: core:PropertyPlantEquipmentClassesDimension
hold_constant:
  - core:PPEOwnershipDimension
missing_policy: missing_combination_is_not_nil
This directly addresses the PPE problem described in the consistency-check explanation, where choosing the wrong dimension to sum across can wrongly imply missing lower-level values are nil.
Family 8 — Modelling suggestions
Purpose:
Tell the filer how to improve the modelling using the taxonomy.
Example:
id: AUTO.PPE.MODELLING.001
type: modelling_suggestion
finding:
  flat_note_detected: true
suggest:
  use_hypercube: core:PropertyPlantEquipmentHypercube
  dimensions:
    - core:PropertyPlantEquipmentClassesDimension
    - core:PPEOwnershipDimension
message: >
  The taxonomy provides a dimensional PPE note model. Consider using the
  PPE class and ownership dimensions rather than flat primary-item-only tagging.
Family 9 — Anti-rules
Purpose:
Block bad generated rules.
Examples:
id: ANTI.PRESENTATION_SUM.001
type: blocked_inference
reason: Do not assume presentation children sum to parent.
id: ANTI.MISSING_ZERO.001
type: blocked_inference
reason: Do not treat missing dimensional facts as zero.

Family 10 — PFS presentation arithmetic consistency (constrained)
Use only when all of these are true:
1. Concept is in a recognised PFS section (SoFP, P&L, CF, SoCE).
2. Parent/child structure is tagged as arithmetic-eligible (via curated allowlist/metadata, not raw presentation alone).
3. Facts are comparable on:
* same period
* same unit
* same entity
* same dimensional context (or explicitly dimensionless policy)
4. Sign policy is explicit (credit/debit inversion handled per statement logic).
5. Missing facts are not auto-zero unless explicitly permitted.

4.4 Dimension normalisation
Materialise default members where appropriate.
But do so carefully.
The FRC explanation notes that dimensions with a default of not applicable may not have natural summation relationships and can create double-counting risk.
So implement:
materialise_defaults=True
exclude_not_applicable_defaults_from_rollups=True

Risks and mitigations
Risk 1 — Over-generating bad rules
Mitigation:
The taxonomy files are the single source of truth and consideration must be given to those relationships in generating rules. Guesswork or custom heuristics should be discussed and documented in detail.
Everything generated is candidate by default.
Use confidence scoring.
Require review before production.
Create anti-rules.
Avoid presentation-derived arithmetic.
Risk 2 — Treating missing facts as zero
Mitigation:
Default missing policy: do_not_treat_missing_as_zero.
Only treat as zero where explicitly justified.
Add dimensional safety rules.
Risk 3 — Hypercube topic names are inconsistent
Mitigation:
Use labels and ELR definitions, not QName alone.
Add manual topic alias map.
Allow topic override files.
Example:
aliases:
  property_plant_equipment:
    - PPE
    - Tangible fixed assets
    - Property plant equipment
Risk 4 — Multiple hypercubes per topic
Mitigation:
Allow topic to contain multiple cubes.
Group by ELR definition, label similarity and primary-item overlap.
Risk 5 — Rule engine becomes too complex
Mitigation:
Keep rule schema explicit.
Do not build a general programming language in YAML.
Use Python for complex rules.

Risk 6 — Findings sound too authoritative
Mitigation:
Use careful wording:
Potential issue
May indicate weak modelling
Consider using
Review whether
Not a filing rejection
